# MLB season simulator — high-level plan

For numbered work packages and release gates, see [docs/EXECUTION.md](docs/EXECUTION.md). For the current task and restart handoff, see [docs/PROGRESS.md](docs/PROGRESS.md). Repository methodology is in [AGENTS.md](AGENTS.md).

## Product contract and initial decisions

Build a desktop application in **Rust + Tauri + Svelte**, with **shadcn-svelte components for application controls, forms, dialogs, navigation, and tables**. Custom baseball views (field, scorecard, charts) will use the same design tokens and accessibility conventions. A user selects one MLB season; its data is imported once, cached locally, and playable offline. The first playable deliverable is a complete, automatically managed head-to-head game between two teams from that season. The long-term deliverable is a full regular-season replay with statistical validation.

Decisions confirmed during planning:

- **Season-end reconstruction**, not forecasting: selected-season statistics may inform player ratings. This uses hindsight; it does not imply we can predict that season before it happens.
- **One audited, well-covered pilot season first**, tentatively 2019; expand season choices only after per-season data and rule audits. A modern post-2020 season is the next contrasting validation target.
- Full-season replays use the **actual schedule and date-appropriate team membership**, with modeled availability and autonomous managers. Historical appearance/transaction information may be incomplete, so availability estimates must be labeled rather than presented as known injuries or active rosters.
- **DuckDB is the initial local-cache choice** because baseball.com's current public data is a DuckLake/Parquet catalog accessible with DuckDB. A packaging/filtered-download spike must prove this works in the Tauri targets and leaves a self-contained offline season file. If not, use SQLite for the local cache behind the same repository interface; do not bind simulation rules to either database.

Scope boundaries: MLB regular-season games only for the pilot; no pitch-by-pitch simulation, 3D animation, multiplayer, or claim of historically exact game results. An exhibition between two chosen teams is not a replay of a specific historical game. Human managerial overrides can follow the first automatic-manager version.

## Source and data contract

[baseball.computer](https://baseball.computer/) describes itself as a **preview** database primarily sourced from Retrosheet. Its [public DuckLake publication notes](https://github.com/droher/baseball.computer/blob/main/docs/ducklake-production.md) document a read-only catalog at `https://data.baseball.computer/baseball/v1/baseball.ducklake`; the [project repository](https://github.com/droher/baseball.computer) contains model definitions, including game starts, personnel, event states, batting, baserunning, batted-ball and fielding statistics, and data-completeness indicators. These are promising inputs, **not yet proof** that every requested feature is complete for every season. The published catalog represents a much larger dataset than one season: the importer must extract a filtered season, not silently download the whole catalog.

1. Audit the pilot season: schedule, AL/NL regular-season filter, source type (play-by-play vs box score), start lineups, roster/appearance dates, stable player/team IDs, batter/pitcher handedness, event outcomes, location/trajectory, fielding opportunities/errors, baserunning, parks and rules. Record coverage and unknowns by table, game and metric; distinguish observed from inferred values.
2. Define a **versioned, normalized season snapshot** containing teams, players/handedness, parks, schedule, known lineup/appearance data, aggregated player/team ratings, contextual event distributions, fielding and baserunning estimates, coverage flags and historical reference totals. Import only the season and minimal shared lookup data. Keep source URL/catalog version or hash, extraction query version, timestamp, schema version and attribution in a manifest.
3. Download over HTTPS with progress, cancellation, disk-space checks, read-only remote access, integrity/row-count checks, retry without duplicate inserts, and atomic promotion of a completed cache. Failed or incomplete imports must not be playable. A completed snapshot needs no network connection to simulate.
4. Reconcile imported counts with the source by season/team/player and preserve the Retrosheet attribution quoted on [baseball.computer](https://baseball.computer/). Review Retrosheet and baseball.computer licensing/attribution terms before distributing data or binaries containing bundled extracts.

**Data signoff:** an auditable per-season coverage report and provenance manifest; source-to-local reconciliation; a measured cold import proving season-filtered transfer and successful offline replay; known missing-data behavior documented. If the pilot fails coverage requirements agreed before implementation, choose another pilot or reduce the claim, never synthesize missing play-level evidence without a flag.

## Architecture and simulation progression

Use a pure Rust `engine` crate (`GameState + legal Decision + seeded RNG -> EventTransition + new GameState`), a `season-data` import/repository layer, a `ratings`/calibration layer, a `manager` policy layer, and a Tauri adapter exposing commands and progress to Svelte. The UI must not determine outcomes. Record seed, source snapshot, rules version, ratings version and event log so a game can be reproduced exactly. Keep original input and simulated results separate.

**Canonical unit: an event transition.** An immutable `EventTransition` records its type, participants, the complete relevant **before** and **after** states, and an explicit outcome/delta. State includes inning/half, outs, score, batting order/current batter and pitcher, and each base occupant's identity and responsibility; the transition records batter and runner advances, outs made, runs scored and statistical credits. Types include plate appearances **and non-PA events** such as steal attempts, pickoffs, wild pitches, passed balls, balks and substitutions. A non-PA event does not advance the batting order or add a plate appearance. One event can include simultaneous effects (for example, a strikeout and a runner advance); do not force every runner movement into a separate PA or lose runner identity. Inning-ending transitions retain outs/runs made on the play even when the next half-inning starts with zero outs and empty bases. The engine validates a transition, applies it atomically, and derives play logs and box scores from the same recorded event stream. Sample outcomes condition on the **before** state; test distributions of both outcomes and state changes, not only aggregate final totals.

### Phase 1 — complete, correct game with simple probabilities

- Model a plate appearance from normalized **era/league baseline + regressed batter and pitcher effects** (rather than multiply batting average by ERA). Start with K, BB/IBB, HBP, HR, ball-in-play out, 1B, 2B, 3B and reach-on-error, conditioned where necessary on outs/runners; rare outcomes fall back to pooled rates. Preserve a coherent probability distribution. Deliberate IBB is a manager decision, not an unconditional batter rate.
- Implement event-by-event base/out state transitions, runner advancement and scoring, sacrifices, double plays, steals/caught stealing, substitutions and pitcher responsibility. A complete nine-inning or extra-inning game needs a basic legal automatic manager for both teams; a pitch-count/workload **proxy** is explicitly not measured pitch-by-pitch fatigue.
- Apply the pilot year's DH, substitution, extra-inning and other relevant rules; define how suspended/tied/forfeit games are handled before a season replay. Present a play log, score, lineups, box score and controls for next play / autoplay / seeded restart.
- Treat first-version errors/advancement as explicit coarse context models, not a claim that fielders already resolve each batted ball. Clearly label the model version in the UI.

**Game signoff:** deterministic reruns match transition-for-transition; every event's `after` state equals the next event's `before` state; legal-state/property tests and edge-case fixtures pass (runner-only events that leave the batter/PA count unchanged, simultaneous advances/outs, three outs and half-inning resets, force plays, double plays, third-out run rules, walk-offs, substitutions, pitcher charges); thousands of random games terminate without impossible states; independent accounting reconciles plate appearances, outs, bases, runs and box scores. UI and offline import/playback tests pass on agreed target platforms.

### Phase 2 — causal contact, defense and baserunning model

- Resolve non-contact outcomes first; then sample **contact type, direction and depth** (and later quality) from batter/pitcher/park tendencies. Assign likely fielding opportunities; estimate conversion to out, hit or error **before** deciding final hit type. Then resolve tag-ups, force plays, throws and extra-base attempts from runner speed, outs, ball location/depth and fielder arm. A recorded “single to left” is already a final outcome and must **not** be independently converted to an out with another range roll: that double-counts defense.
- Add effective handedness, including switch hitters and missing/ambiguous records. Hierarchically shrink sparse L/R splits toward player/league estimates; distinguish batter and pitcher effects from park and defense so those influences are not counted twice.
- Estimate range by position and opportunity/context where the source supports it; estimate error probability **per actual opportunity**, not by treating `1 - fielding percentage` as the chance of an error on every ball in play. Estimate OF arm/catcher effects from eligible runner/throw opportunities, not raw assists or caught-stealing totals alone. When opportunity quality or location is missing, use a neutral prior and expose uncertainty. Historical data may not identify true range or arm strength independently of positioning, teammates and scorer judgment.
- Add calibrated steals (attempt *and* success), pickoffs, wild pitches/passed balls, advancement on contact, sacrifice choices and appropriate conditional dependencies. Keep event-level and aggregate diagnostics for every new factor.

**Mechanism signoff:** controlled counterfactual tests show stronger LF range changes appropriately located BIP conversion but not K/BB rates; stronger OF arm changes advance/throw outcomes but not contact rates; faster runners affect steal and eligible advance rates; handedness and park effects behave in expected directions. Compare conditional distributions on held-out opportunities, not just total hits/runs.

### Phase 3 — full-season management and replay

- Execute the historical schedule in order with team/park/era context. Maintain persistent rosters, standings, cumulative stats, pitcher workload and rest. Infer date-appropriate membership/availability conservatively from source appearances and any verified roster/transaction records; flag uncertainty. Do not use future game outcomes to decide current substitutions.
- Manager policies choose starters/rotation, lineups, bullpen entry and leverage roles, pitch limits/rest, pinch hitting/running, defensive replacements, steals and tactical choices. All choices are constrained by eligible personnel and era rules (including DH and pitcher minimum-batter rules where applicable). Separate **policy** from the engine so it can be benchmarked/replaced without altering outcome probabilities.
- Support two evaluation runs: **fixed-opportunity/controlled** simulations to isolate player skill and game mechanics; **free replay** to test lineup, availability, bullpen and playing-time decisions together. Report which mode produced each comparison.

**Season signoff:** schedule/roster eligibility and transaction-like transitions pass invariants; the season completes reproducibly; manager usage is compared with historical distributions for starts, PA/IP, rest days, relief roles and substitutions conditional on score/inning/leverage, with uncertainty noted for inferred availability.

## Statistical validation and release gates

Accuracy is **distributional**, not exact reproduction of one player's historical line or one game's score. Before fitting each new model, preregister metrics, sample filters, uncertainty intervals and tolerances from the pilot audit. Run many independent seeded games and, later, **at least 100 full-season replications** (target 200 for rarer outcomes) for the signoff suite; save seeds, source snapshot and model versions. Report observed values alongside simulated mean, its Monte Carlo confidence interval, the distribution's 95% predictive interval, bias and predictive-interval coverage. Use paired seeds and a simpler baseline when comparing model revisions.

- **Core checks:** league/team runs per game and scoring distribution; PA rates for K, BB, HBP, HR, hits by type, ROE and GIDP; conditional before-to-after base/out/runner transition frequencies, including non-PA events; park and batter/pitcher matchup splits; high-leverage and extra-inning behavior. Provisional league-level targets for common PA rates and runs/game: simulated expectation within **2–3% relative** of historical. Final thresholds must be agreed before calibration, account for genuinely rare events and include team-level diagnostics.
- **Player checks:** for hitters and pitchers with meaningful opportunities, compare rates with exposure held fixed as well as free-replay totals. Group by opportunity size; check whether nominal 90% prediction intervals contain about 85–95% of observed lines **without making those intervals vacuously wide**. Track worst systematic biases, not only mean error. Team wins and individual counting totals remain stochastic.
- **Defense/runner checks:** by position and opportunity, compare BIP conversion, error rate, assists/putouts where definable, advancement attempts and successes, steals/CS, and outfield throws; separate missing-data coverage from model errors. A league-wide fit cannot excuse a wrong conditional mechanism.
- **Generalization checks:** matching a season used to derive its own ratings is **in-sample reconstruction**. For actual predictive claims, fit without the held-out games/opportunities (cross-fitting) or use only data available before each game, then compare log loss/Brier score and calibration to a simple league/player baseline. Validate on another audited season/era before expanding support.
- **Regression/performance checks:** automated unit, property, importer, integration and end-to-end UI tests; fixed golden seeds and benchmark runs for memory, CPU, import volume and season runtime. Preserve failing seeds and raw diagnostics. A slower or more elaborate engine is not an improvement unless it wins on the preregistered held-out and simulation criteria.

Release gates are sequential: **data feasibility → correct playable game → defense/runner fidelity → managed season → multi-season support**. Each gate needs test artifacts, a coverage report, known limitations and explicit product signoff. Do not advertise unsupported years as equivalent to the pilot; show a per-season capability grade for play-by-play, handedness, fielding and rules.

## Decisions to revisit at the feasibility gate

Confirm pilot year after the coverage audit; target desktop OSes and DuckDB/DuckLake extension packaging; quantitative coverage and performance budgets; exact model signoff tolerances; and whether historical replay follows actual lineups when known or generates them from date-appropriate personnel. None should be silently decided by missing data.
