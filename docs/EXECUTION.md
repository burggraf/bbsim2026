# Execution roadmap

[PLAN.md](../PLAN.md) is the product/modeling contract. This file defines **work packages and acceptance evidence**. [PROGRESS.md](PROGRESS.md) is the **only live status ledger**; do not maintain a competing task-status list here. [AGENTS.md](../AGENTS.md) defines how to work and leave a handoff. Task IDs are stable references for commits, reports and handoffs; a task is not done merely because code exists.

## Order and initial focus

Data feasibility (F) → deterministic event engine (E) → playable probabilistic game (P) → conditional defense/runner fidelity (A) → managed season (S) → additional seasons (X). Do not build the Tauri UI first: the risk is source coverage and the correctness of game transitions. Work on the smallest auditable slice; split tasks further in `PROGRESS.md` if needed without silently changing gate requirements.

**Start with F-01.** The first implementation change should be a reproducible, read-only data audit of candidate **2019**, not a full app scaffold. If the audit rejects 2019, choose another pilot through F-04 and record why. Use the public baseball.computer DuckLake catalog as a candidate source, not as a guarantee that every column is available in every year.

## Gates and signoff

- **G0 — data:** F-04 has a coverage report, fixture reconciliation, measured filtered/offline import, attribution/licensing review and an explicit pilot/storage/OS decision. Stop or rescope if required event fields are not reliable.
- **G1 — engine:** E-03 has passing deterministic fixtures and property tests for legal states, half-inning continuity and independent statistic accounting. The approved [accounting matrix](engine/g1-accounting-scope.md) governs completeness and required evidence; scope approval is not gate signoff. Source ambiguities remain visible; no claim of predictive accuracy.
- **G2 — playable game:** P-03 produces a complete seeded game offline; full Rust and frontend applicable checks plus game-level invariants pass on agreed targets. Publish baseline outcome diagnostics and known coarse-model limitations.
- **G3 — mechanisms:** A-04 shows calibrated conditional effects (handedness, BIP, errors, steals/advances) and counterfactual isolation, using thresholds fixed **before** model tuning. A better in-sample fit alone does not pass.
- **G4 — managed season:** S-03 completes reproducible historical-schedule replays with legal rosters/managers and 100+ season ensemble evidence. Distinguish reconstruction from out-of-sample prediction and fixed-opportunity from free replay.
- **G5 — expanded seasons:** X-01 documents the second season's data/rules differences and independently passes its applicable gates. Future years require their own audit.

A gate is signed off only when its evidence is linked in `PROGRESS.md`, checks and failures are reported, and the maintainer records the go/no-go decision. For a blocked gate, keep the failing evidence and state the alternative: fix, narrow scope or stop. Accuracy thresholds are proposed and recorded before fitting/evaluating the relevant model; changes after observing results require a dated rationale and a new independent evaluation, never silent edits to get green.

## Handoff and artifact conventions

Keep small reproducible SQL/scripts, fixtures and concise audit reports in the repo when permitted. Store large downloads, caches, raw datasets, credentials and generated run logs outside Git; reference their provenance and reproduction command instead. Every completed task gets: a linked artifact or commit, exact checks and results, remaining limitations, and its gate impact in `PROGRESS.md`. On interruption, record the current task, what changed, what remains unverified and the **next exact action** so a new session can resume without relying on chat history.
